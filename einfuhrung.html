    1.1. Die Rolle von Flask in einer Webanwendung

    Eine Webanwendung wird häufig in Schichten aufgebaut, wobei jede Schicht nur mit den benachbarten Schichten kommuniziert:

    • Die Web-Schicht empfängt die HTTP-Anfragen des Browsers und liefert ihm HTML-Seiten zurück. Dies ist die Schicht, bei deren Programmierung [Flask] uns hilft;
    • Die Geschäftsschicht enthält die Geschäftsregeln der Anwendung (z. B. „Ein Patient kann nur einen bevorstehenden Termin haben“). Sie weiß nichts über das Web: Sie könnte ebenso gut eine Kommandozeilenanwendung bedienen;
    • Die Datenzugriffsschicht (DAO-Schicht, [DAO] für [Data Access Object]) liest aus der Datenbank und schreibt in sie. Wir verwenden [SQLAlchemy], einen ORM ([Object Relational Mapper]), der die Zeilen der Tabellen auf [Python]-Objekte abbildet.

    Die Web-Schicht selbst folgt dem Modell [MVC] ([Model – View – Controller]):

    • Der Controller (C) ist eine Menge von [Python]-Funktionen, die als Aktionen bezeichnet werden und von denen jede einen Anfragetyp verarbeitet (zum Beispiel [GET /schedule]). Eine Aktion liest die Anfrageparameter, ruft die Geschäftsschicht auf und wählt dann die anzuzeigende View aus;
    • Das Modell (M) ist die Menge der Daten, die die Aktion an die View übergibt;
    • die View (V) ist eine [Jinja2]-Datei (Erweiterung [.html]): eine HTML-Seite, die Ausdrücke [{{ ... }}] und Anweisungen [{% ... %}] ([{% if %}], [{% for %}] ...) enthält, die die [Jinja2]-Engine durch Daten aus dem Modell ersetzt.

    Ein Hinweis zur Terminologie, um Verwirrung zu vermeiden: Die Dokumentation von [Flask] bezeichnet die Funktion, die eine Anfrage verarbeitet, als eine „View-Funktion“ und die [Jinja2]-Datei als „Template“. Dieses Dokument verwendet die Terminologie des Modells [MVC] sowie die der Kurse [Spring MVC] und [ASP.NET Core MVC] : Die Funktion, die eine Anfrage verarbeitet, ist eine Aktion, die [Jinja2]-Datei, die die Seite erzeugt, ist eine View, und der Begriff „Template“ bezeichnet die gemeinsame View, von der andere Seiten erben (Kapitel 4).

    Die Verarbeitung einer Anfrage folgt den nummerierten Schritten im Diagramm:

    • 1: Der Browser sendet eine Anfrage, etwa HTTP oder [GET /schedule?doctorId=1&day=2026-09-26];
    • 2: Der Webserver empfängt die Anfrage und übergibt sie an die [Flask]-Anwendung. Während der Entwicklung ist dieser Server [Werkzeug], die Bibliothek, auf der [Flask] aufbaut; in der Produktion wird es ein Server wie [Waitress] oder [Gunicorn] sein. [Werkzeug] vergleicht den angeforderten Pfad mit den Routen der Anwendung und wählt die Aktion aus, die für diese Anfrage zuständig ist: Das ist das Routing. Bevor die Anfrage die Aktion erreicht, kann sie noch Funktionen durchlaufen, die für alle Anfragen ausgeführt werden ([before_request]), die wir in späteren Kapiteln untersuchen werden;
    • 3: Die Aktion fordert die benötigten Daten bei der Geschäftsschicht an; falls nötig, wendet sich die Geschäftsschicht an die [DAO]-Schicht, die die Datenbank [MySQL] per SQL abfragt;
    • 4: Die Aktion erstellt das Modell M der View und weist die [Jinja2]-Engine an, die Seite zu erzeugen (Funktion [render_template]);
    • 5: Die von der View erzeugte HTML-Seite ist die Antwort der Aktion, die [Flask] an den Browser zurückgibt.

    [Flask] ist eines der beiden am häufigsten verwendeten Web-Frameworks der [Python]-Welt, neben [Django]. Frei und quelloffen, läuft es überall dort, wo [Python] läuft ([Windows], [Linux], [macOS]). Es ist ein Micro-Framework: Sein Kern ist bewusst klein gehalten (Routing, Anfragen und Antworten, Sitzungen, [Jinja2]-Views), und alles Übrige (Formularvalidierung, Datenbankzugriff, Authentifizierung usw.) übernehmen Bibliotheken, die der Entwickler auswählt. Während [Spring Boot] von sich aus einen kohärenten Satz von Komponenten konfiguriert, [Flask] überlässt es dem Entwickler, seine eigenen zusammenzustellen: Die Anwendung ist transparenter, und man sieht alles, was in ihr vorgeht. Gerade das macht es zu einem guten Werkzeug zum Lernen: Fast nichts ist verborgen. [Flask] kann sowohl Server erstellen, die JSON an einen [JavaScript]-Client ([Angular], [React], [Flutter] ...) zurückgeben, als auch herkömmliche Webanwendungen, bei denen der Server die HTML-Seiten erzeugt und der Browser sie nur anzeigt. Dieses Dokument behandelt diesen zweiten Anwendungsfall. Zwei Konzepte von [Python] kehren auf jeder Seite wieder: Dekoratoren ([@app.get("/")], [@app.before_request] ...), die eine Funktion mit einer Aufgabe verknüpfen, und die explizite Übergabe der Objekte, die jede Funktion benötigt, während [Spring] sie automatisch injiziert.

from datetime import date
from pathlib import Path

from flask import Blueprint, Flask, request

from controllers.pages import pages

# Bootstrap, von den Beispielen gemeinsam genutzt: der Ordner examples/common/bootstrap,
# ausgehend vom Speicherort DIESER Datei bestimmt (und nicht vom aktuellen Ordner)
BOOTSTRAP = Path(__file__).resolve().parent.parent / "common" / "bootstrap"


def create_app():
    app = Flask(__name__)
    app.jinja_env.trim_blocks = True
    app.jinja_env.lstrip_blocks = True
    # ein Blueprint ohne Routen, der nur statische Dateien ausliefert: der
    # Ordner BOOTSTRAP, unter der URL /bootstrap/...
    app.register_blueprint(Blueprint("bootstrap", __name__, static_folder=BOOTSTRAP,
                                     static_url_path="/bootstrap"))
    app.register_blueprint(pages)
    • Zeile 11: der Pfad zum Ordner [common/bootstrap]. [__file__] ist der Pfad zur aktuell ausgeführten Datei ([app.py]); [Path(...).resolve()] macht daraus einen absoluten Pfad; [.parent] bezeichnet den Ordner, der sie enthält ([15-layout]), und [.parent.parent] bezeichnet den übergeordneten Ordner ([examples]). Der Operator [/] eines [Path] -Objekts fügt dem Pfad ein Element hinzu, und zwar mit dem richtigen Trennzeichen ([\] unter [Windows], [/] sonst). Der Pfad hängt also nicht vom aktuellen Ordner ab: Das Beispiel findet [Bootstrap] unabhängig davon, von wo aus es gestartet wird;
    • Zeilen 20–21: Ein Blueprint ist eine in der Anwendung registrierte Gruppe von Routen (siehe Beispiel 02). Dieser Blueprint hat keine Routen: Er dient ausschließlich dazu, den Ordner [common/bootstrap] (Parameter [static_folder]) unter der URL [/bootstrap] (Parameter [static_url_path]) bereitzustellen. Eine Seite kann so das Stylesheet [/bootstrap/css/bootstrap.min.css] verwenden.

    Die übrigen Zeilen dieser Datei werden in Beispiel 15 erklärt.
